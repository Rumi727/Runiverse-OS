# 질문 목록

단계별로 물을 질문입니다. 전부 물을 필요는 없습니다. 답이 이미 대화나 `AGENTS.md`에 있으면 건너뜁니다. 답에 따라 문서가 달라지는 질문은 반드시 묻습니다.

`AskUserQuestion` 한 번에 질문은 최대 4개입니다. 비슷한 주제끼리 묶어 라운드를 나눕니다. 선택지는 탐색에서 찾은 구체적인 이름으로 채웁니다. "A 패키지"처럼 쓰지 말고 실제 패키지·타입 이름을 넣습니다.

## 0단계: 탐색 전

### 범위
- 문서화할 패키지와 시작점은 무엇인가요? (공개 API 진입점, 예: `NoteBlockSource.Play()`)
- 밀접하게 연관된 다른 패키지도 문서화해야 하나요? 그 코드는 같은 패키지인가요, 별도 패키지인가요?
  - 별도 패키지라면 각 패키지에 **독립 문서**를 두고, 하위 패키지 문서는 상위 패키지를 언급하지 않습니다. 이것을 확인합니다.
- 독자는 누구인가요? (C#은 알지만 이 도메인은 처음인 사람 / 이 코드베이스 기여자 / 미래의 나)
- 문서의 목적은 무엇인가요? (구조 파악 / 디버깅 참고 / 새 기여자 온보딩 / 설계 검토)

### 이름과 상태
- 최근에 개명했거나 곧 개명할 패키지, 타입, 레지스트리 id가 있나요?
- 지금 코드는 커밋되어 있고 문서를 쓰는 동안 바뀌지 않나요?
  - 바뀌지 않으면 장마다 코드를 다시 확인하지 않습니다.
  - 바뀐다면 기준 커밋을 언제 다시 잡을지 묻습니다.
- 기준 커밋은 현재 HEAD로 하나요?

### 형식과 위치
- 형식: Markdown만 / Markdown + Mermaid / + 정적 SVG / + 인터랙티브 HTML
- 위치: 각 패키지 `Documentation~/`(추천, Unity가 임포트하지 않음) / 저장소 루트 `docs/` / 기타
- 언어: 한국어(기존 README와 같음) / 영어 / 둘 다
- 패키지에 README가 없을 때 새로 만들지, `Documentation~/README.md`만 둘지

## 2단계: 탐색 후, 쓰기 전

### 용어 대응
사용자가 쓴 단어를 탐색에서 찾은 심볼 후보와 짝지어 확인합니다.
- 예: "말씀하신 '트랜스파일러'는 `NBSPreviewTransport`(MonoBehaviour 없이 `INBSTransport`를 구현하는 프리뷰용 트랜스포트)인가요? Harmony transpiler는 코드에 없습니다."
- 후보가 여러 개면 선택지로 나열합니다.

### 장 구성과 깊이
- 제안한 장 목록(파일 이름 + 한 줄 내용)이 괜찮나요? 빠진 것, 합치거나 나눌 것이 있나요?
- 장마다 깊이를 정합니다. (`multiSelect`로 "줄 단위로 쓸 장"을 고르게 해도 됩니다.)
  - **줄 단위:** 발췌한 코드의 거의 모든 줄을 ①② 표시로 설명
  - **핵심만 줄 단위:** 핵심 메서드만 줄 단위, 나머지는 표와 그림
  - **요약:** 역할, 호출 관계, 주의점만
- 주변부지만 요약으로는 부족할 만큼 복잡한 부분이 있나요? (예: 에디터 프리뷰, 직렬화, 리셋 처리)
- 한 메서드가 매우 길 때: 전부 발췌할까요, 핵심 구간만 발췌하고 나머지는 `…`로 줄일까요?
- XML 주석 내용을 문서에 옮길까요, 링크만 할까요?
- 사용 예제 코드를 넣을까요? 넣는다면 실제 코드베이스의 사용처를 인용할까요, 최소 예제를 새로 쓸까요?

### 모호한 코드와 API
탐색에서 모은 항목을 한 라운드에 최대 4개씩 묻습니다. 각 질문에 파일:줄과 관찰한 동작을 한 문장으로 적습니다.
- 선택지: **의도된 동작**(문서에 설명) / **버그일 수 있음**("관찰된 동작"으로 기록) / **모르겠음**("관찰된 동작"으로 기록) / **문서에서 빼기**
- 자주 나오는 유형:
  - 이름이 암시하는 것과 실제 동작이 다른 곳 (예: `index`라는 필드가 연속이 아님)
  - 같은 개념에 두 가지 규칙이 쓰이는 곳 (예: 같은 시각의 Stopper를 한 곳은 포함하고 다른 곳은 제외)
  - 접두사·대소문자·경계값(포함/제외) 처리가 일관되지 않은 곳
  - 실패 경로에서 일부 상태만 갱신되는 곳
  - 화면이나 API마다 같은 값을 다른 출처에서 읽는 곳 (예: 현재 위치를 세 곳에서 다르게 계산)
  - 버전·포맷 분기에서 오래된 버전 처리가 달라 보이는 곳
  - 스레드 경계에서 잠금 없이 읽는 값이 의도인지
- 공개 API인데 사용처가 없는 멤버: 문서에 넣을지 묻습니다.

### 기존 문서와 코드 불일치
- "README의 'X는 `Foo()`를 부른다'는 설명이 실제(`File.cs:131`)와 다릅니다." 선택지: README 고치기 / 새 문서에만 실제 동작을 적기 / 그대로 두기
- 기존 README에 새 문서 링크를 한 줄 넣을지 (기존 파일 수정이므로 보고에 밝힘)

### 인터랙티브 페이지
사용자가 인터랙티브를 원했을 때만 묻습니다.
- **무엇부터:** 정적인 그림으로 가장 이해하기 어려운 현상은 무엇인가요? 후보는 탐색에서 찾은 시간축·스케줄링·상태 전이 중에서 제시합니다.
  - 예: "믹스 블록 위에서 워커가 lookahead 창을 미끄러뜨리며 예약하는 모습 / `time`과 `outputTime` 보간 / 노트 배치 8가지"
- **축소 모델:** 실제 코드와 같은 식을 쓸 부분과 단순화할 부분은 무엇인가요? 예를 들어 워커 깨어남의 지터는 난수로, 블록 크기는 실제 값으로 합니다.
- **조작:** 슬라이더나 버튼으로 바꿀 값 (예: tempo, 블록 크기, 버퍼 수, 워커 간격, lookahead, 지터)과 명령 (재생, 일시 정지, seek, 반복)
- **증명:** 화면에 보여 줄 불변 조건은 무엇인가요? (예: "예약한 소리의 시작 오차 = 0샘플")
- **상태 표시:** 내부 상태 표, 이벤트 로그가 필요한가요?
- **호스팅:**
  - 저장소 파일 + githack 링크: public 저장소에서 push한 뒤부터 동작합니다.
  - claude.ai 아티팩트: 비공개이고 바로 열립니다.
  - 둘 다
- 여러 개 만들지, 페이지 하나에 탭으로 넣을지

## 3단계: 쓰는 도중

새로 만난 모호한 곳을 몇 개씩 모아 묻습니다.
- "`Foo`는 실패하면 `bar`를 갱신하지 않습니다. 다음 호출에서 다시 시도하려는 의도인가요?"
- 한 장의 분량이 예상보다 크게 늘면, 장을 나눌지 줄일지 묻습니다.

  - 기존 README 링크 커밋

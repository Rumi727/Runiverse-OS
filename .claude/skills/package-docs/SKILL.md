# 패키지 작동 원리 문서 작성

API 시작점에서 출발해 내부 코드를 따라 들어가며, C#을 아는 독자가 구조를 한눈에 이해하도록 그림과 줄 단위 해설로 문서를 쓰는 절차입니다.

**완성 예시:** [`Packages/io.github.rumi727.runios.nbs/Documentation~/`](../../../Packages/io.github.rumi727.runios.nbs/Documentation~/README.md)와 그 문서가 링크하는 sound, fmod, uielements(`Grids`)의 `Documentation~`. 형식이 헷갈리면 이 파일들을 열어 보고 따라 합니다. 내용을 복사하지는 않습니다.

## 핵심 원칙: 추측하지 말고 묻는다

이 스킬의 중심은 **질문 단계**입니다. 문서의 가치는 정확성에서 나오고, 사용자는 자기 코드의 의도를 알지만 에이전트는 모릅니다. 다음은 반드시 질문으로 확정합니다.

- 범위, 패키지 경계, 이름(개명 여부 포함)
- 어디를 줄 단위로 쓰고 어디를 요약할지
- 사용자가 쓴 용어가 코드의 어떤 심볼인지
- 의도가 불분명한 코드, 버그처럼 보이는 동작, 코드와 맞지 않는 기존 문서
- 인터랙티브 페이지를 무엇부터, 어떤 모델로 만들지

`AskUserQuestion`은 한 번에 질문 1~4개, 선택지 2~4개입니다. 한 라운드에 다 넣지 말고 아래 단계마다 여러 라운드로 나눕니다. 질문은 단독으로 읽혀야 하므로, 탐색에서 알게 된 사실을 질문 문장에 짧게 넣습니다. 질문 목록 전체는 [references/questions.md](references/questions.md)에 있습니다. 상황에 맞는 것을 골라 쓰고, 목록에 없는 의문도 생기면 묻습니다.

추천 선택지를 첫 번째에 두고 "(추천)"을 붙입니다. 사용자의 답이 선택지 밖 자유 서술이면 그 문장을 그대로 따릅니다.

## 단계

### 0단계: 탐색 전 질문 (1~2 라운드)

코드를 읽기 전에 [questions.md의 0단계](references/questions.md#0단계-탐색-전)를 묻습니다. 특히 다음은 이전 작업에서 사용자가 중간에 바로잡아야 했던 것들이라 처음에 확인합니다.

- 관련 코드가 **별도 패키지**인지. 별도 패키지라면 각 패키지의 `Documentation~`에 **그 패키지만으로 읽히는 독립 문서**를 쓰고, 상위 패키지 문서가 링크합니다.
- 진행 중이거나 최근의 **패키지 개명**(이름, 레지스트리 id).
- 코드가 **커밋되어 고정**되었는지. 고정이면 장마다 코드를 다시 읽지 않습니다(토큰 절약). 줄 번호가 필요할 때만 `grep -n`으로 확인합니다.

### 1단계: 탐색

- `AGENTS.md`의 규칙을 따릅니다. 코드 파일은 고치지 않습니다.
- 공개 API 진입점에서 호출 그래프를 따라갑니다. 범위가 넓으면 `Explore` 서브에이전트로 병렬 조사합니다.
- 탐색하면서 다음 네 목록을 따로 모읍니다. 2단계 질문의 재료입니다.
  1. **용어 대응:** 사용자가 쓴 단어 → 후보 심볼
  2. **모호한 코드/API:** 이름과 동작이 어긋나는 곳, 같은 개념이 두 규칙을 따르는 곳, 의도인지 버그인지 알 수 없는 곳
  3. **기존 문서와 코드의 불일치:** README나 XML 주석이 실제 코드와 다른 곳(파일:줄 포함)
  4. **그림이 꼭 필요한 개념:** 시간축, 스레드, 상태 전이, 좌표 변환처럼 글로는 안 읽히는 것

### 2단계: 탐색 후 질문 (여러 라운드)

[questions.md의 2단계](references/questions.md#2단계-탐색-후-쓰기-전)를 묻습니다. 순서는 다음을 권장합니다.

1. **용어 대응 확인.** 예: 사용자가 "트랜스파일러"라고 부른 것은 `NBSPreviewTransport`였습니다.
2. **장 구성과 깊이.** 장 목록을 제시하고, 장마다 "줄 단위 / 핵심만 줄 단위 / 요약"을 묻습니다. 주변부라도 요약으로는 부족할 만큼 복잡한 곳이 있는지 따로 묻습니다(예: NBS 프리뷰).
3. **모호한 코드.** 모은 항목을 한꺼번에 묻습니다. 항목마다 "의도된 동작 / 버그 / 모름"을 선택지로 줍니다.
   - "의도"는 그대로 설명합니다.
   - "버그"나 "모름"은 문서에 **"관찰된 동작"**으로만 적고, 버그라고 단정하거나 수정을 제안하지 않습니다.
   - 묻지 않은 항목을 사실처럼 쓰지 않습니다.
4. **기존 문서 불일치.** 고칠지, 문서에만 적을지 묻습니다. 묻지 않고 기존 파일을 고치지 않습니다.
5. **인터랙티브 페이지.** [questions.md의 인터랙티브 절](references/questions.md#인터랙티브-페이지)을 묻습니다. 어떤 현상부터 만들지, 축소 모델과 슬라이더, 증명으로 보여 줄 불변 조건, 호스팅 방법입니다.

그다음 계획을 정리해 승인을 받습니다(plan mode라면 `ExitPlanMode`). 사용자가 계획을 거절하며 정정하면 그 정정을 계획에 반영하고, 필요하면 해당 질문을 다시 합니다.

### 3단계: 작성

형식 규칙은 [references/style.md](references/style.md)에 있습니다. 작성 전에 한 번 읽습니다.

- **순서:** 가장 아래 계층(다른 문서가 선행으로 링크할 문서)부터 씁니다. 파일 하나가 끝날 때마다 디스크에 저장합니다.
- 쓰는 도중 새로 모호한 곳을 만나면 추측하지 말고 묻습니다. 몇 개 모아서 한 라운드로 물어도 됩니다.
- **그림:** SVG는 [scripts/svg_kit.py](scripts/svg_kit.py)를 import하는 생성 스크립트를 스크래치패드에 만들어 그립니다. 생성 스크립트는 저장소에 넣지 않습니다.
- **인터랙티브 HTML:** 작성 전에 `artifact-design` 스킬을 로드합니다. 형식 규칙은 style.md의 인터랙티브 절을 따릅니다.

### 4단계: 검증

출력은 스크래치패드에 씁니다. 다만 내장 브라우저는 세션 폴더 안의 파일만 열 수 있으므로, 브라우저로 볼 파일은 저장소 루트에 점으로 시작하는 임시 파일(예: `.mermaid-check-tmp.html`)로 만들고 확인 직후 지웁니다. 결과 파일을 저장소에 남기지 않습니다.

1. **링크:** `python3 .claude/skills/package-docs/scripts/checklinks.py <문서 루트 또는 .md>...`
   - 상대 경로, 헤딩 앵커, `#L번호` 범위, 그 줄 근처에 링크 라벨의 심볼이 있는지 검사합니다.
   - `SYMBOL?`는 라벨이 파일 이름뿐일 때 오탐이 납니다. 직접 확인하고, 반복되는 단어는 `--ignore-word`로 뺍니다.
2. **Mermaid:** `python3 .claude/skills/package-docs/scripts/mermaid_gallery.py .mermaid-check-tmp.html <문서 루트>...`로 모든 블록(목록 안에 들여 쓴 블록 포함)을 한 페이지에 모읍니다.
   - 내장 브라우저로 열고 `javascript_tool`로 `window.__mermaidReport`를 읽어 오류 블록을 확인합니다.
   - 내장 브라우저는 `file://` 페이지를 `data:`로 열어 상대 경로 자산이 깨집니다. 그래서 스크립트가 모든 것을 한 파일에 넣습니다.
3. **SVG:** 브라우저 확대·스크린샷은 작은 글씨 겹침을 잡기에 믿을 수 없습니다.
   - `rsvg-convert -w 1400 <svg> -o <스크래치>/png/<이름>.png`로 변환한 뒤 `Read`로 이미지를 직접 봅니다.
   - 라벨 겹침, 패널 밖으로 넘친 글씨, 축 눈금을 확인합니다.
4. **인터랙티브 HTML:** 내장 브라우저에서 엽니다.
   - 콘솔 오류가 없어야 합니다.
   - 모든 조작을 한 번씩 해 보고, 표시하는 불변 조건이 유지되는지 봅니다.
   - 375px 폭에서 가로 스크롤이 없어야 합니다.
5. `git diff --stat <기준 커밋> HEAD -- Packages`로 작성 중 코드가 바뀌었는지 확인합니다. 바뀌었으면 줄 링크가 밀렸을 수 있으니 갱신할지 묻습니다.
6. `git status --short`로 저장소에 임시 파일이 남지 않았는지 확인합니다.

### 5단계: 마무리 질문과 보고

- 기존 `README.md`에 새 문서 링크를 넣을지 묻습니다. 넣었다면 보고에 밝히고, 되돌릴 수 있다고 적습니다.
- 보고에 다음을 포함합니다.
  - 만든 문서의 위치와 각 문서의 범위
  - 검증한 것과 하지 못한 것(예: GitHub 자체 Mermaid 렌더러, 다크 테마)
  - "관찰된 동작"으로 적은 항목, 고치지 않은 기존 문서 불일치
- **커밋은 요청받았을 때만** 합니다. 요청받으면 `AGENTS.md`의 커밋 규칙대로 패키지별 문서 커밋과 기존 README 링크 커밋을 나누고, `Co-Authored-By` 기준을 적용합니다.
